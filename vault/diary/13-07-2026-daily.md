# Daily — 13-07-2026

## Resumo
Dia inteiro dedicado ao feature de geração de prompt em background para o Agents V2. Comecei consolidando as notas de sexta e escrevendo spec + plano (`2026-07-13-agents-v2-prompt-background`), e implementei o plano quase de ponta a ponta: schema Prisma com `promptStatus`, repositório do core, fila BullMQ (`agent-prompt-queue`) seguindo o padrão de `modules/queues`, processor com falha imediata (attempts 1) e a classe genérica `agent.socket.ts` no core para emitir o status via WebSocket. A noite foi de depuração pesada de por que o evento FAILED/READY não chegava ao front — a causa se revelou ambiental (`WEBSOCKET_URL`/`.env.local` apontando para o servidor errado). Fechei com toasts de sucesso/erro, o card em estado BUILDING/FAILED, skeleton no modo edição e a documentação do fluxo no vault.

> [!tip] Decisoes
> - Regra de projeto: migrations são sempre manuais — proibido criar/aplicar migration, mesmo em dev.
> - Construção do prompt do modo BASIC em background via fila BullMQ, seguindo o padrão de `chatfunnel-services/src/modules/queues` (não implementação genérica ad-hoc).
> - Nome genérico `agent_queue.service.ts` / `agent.socket.ts` — tudo que o agent precisar de fila/socket fica nessas classes.
> - Sem auto-retry: attempts 1, falha imediata e erro enviado via WebSocket; retry é manual pelo usuário.
> - Toasts de criação/edição usam o tipo info ("Criando/Atualizando"), não sucesso — "criado com sucesso" seria falso enquanto o agente está BUILDING.

> [!warning] Bloqueios
> - Erro de geração de prompt (`Falha ao gerar prompt`) não chegava ao front — causa ambiental: `WEBSOCKET_URL` no `services.env` apontando para o lugar errado.
> - `SignalR connect_error: xhr poll error` — services conectando no WebSocket errado; corrigido apontando `.env.local`/`services.env` para localhost.
> - Processo `[metrics]` continuava vivo após encerrar o servidor (mortos manualmente por PID).
